* Goal
Enhance the =propose-edit= tool to display diffs directly within the expanded tool call UI
with syntax highlighting, and add generic action button infrastructure so tools can attach
custom behaviors (like "Open diff") to the tool call header.

Specifically:
1. Embedded diff rendering: When the tool call is expanded, show the full diff content
   with proper syntax highlighting (leveraging existing =diff-mode= infrastructure).
2. Action buttons: Register a generic mechanism for tools to attach buttons (labeled
   "Open diff", etc.) to the tool call header without blocking the UI.
3. Generic tool actions: Infrastructure usable by any tool, not just =propose-edit=.

* Requirements recap
- The diff must be readable inline without switching buffers.
- The "Open diff" button must switch to the review buffer while keeping the tool
  call region collapsed (no forced expansion or refocus on close).
- Action handlers are tool-owned lambdas, not global function references, so tools
  have full closure control.
- Read-only, syntax-highlighted rendering (no interactive hunks inline yet).
- Maintain backward compatibility: tools that don't return =:actions= should work as before.
- Test coverage for: action invocation, button interaction, diff rendering, marker stability.

* Proposed architecture

** Tool response schema (enhanced)
Tools can now return an =:actions= key alongside =:ui= and =:content=:

#+begin_src elisp
(list :content "..."
      :ui (list :header "..."
                :state 'success
                :body "...")
      :review-buffer "..."  ;; for propose-edit
      :actions (list (list :label "Open diff"
                           :handler (lambda () (pop-to-buffer review-buffer)))
                     (list :label "Other action"
                           :handler (lambda () ...)))))
#+end_src

** Rendering flow (benedict-chat-render.el)
1. When rendering tool call header, check for =:actions= in the UI spec.
2. If present, insert action buttons **after** the header text (on the same line or wrapped).
3. Buttons use the existing =insert-text-button= mechanism with a dedicated =action= property
   pointing to the handler lambda.
4. Clicking a button runs its handler in the context of the chat buffer (not the tool result).

** Diff embedding (new internal function)
1. Add =benedict-chat--format-diff-body= to prepare diff content for display.
   - Takes diff string + optional language hint.
   - Returns formatted string suitable for inserting into tool body.
2. Integrate into tool rendering so =:body= can contain the diff when desired.
3. Use existing code block formatting infrastructure to ensure proper syntax highlighting.

* Implementation plan

** Phase 1: Generic action button infrastructure
1. Extend =benedict-chat--normalize-tool-ui= to accept and validate =:actions= list.
   - Each action must have =:label= and =:handler= (fn with no args).
   - Validate =:handler= is callable.
2. Add =benedict-chat--render-tool-actions= to insert buttons into the tool header.
   - Buttons appear after the header text, separated by spaces.
   - Use =insert-text-button= with 'action property pointing to handler.
   - Clicking invokes the handler immediately.
3. Update =benedict-chat--render-tool-item= to call =benedict-chat--render-tool-actions=
   after rendering the header text (before the newline).
4. Test: Verify button insertion, handler invocation, and marker stability.

** Phase 2: Diff embedding in propose-edit
1. Add =benedict-chat--format-diff-body= to format diff strings for display.
   - Takes (diff root) and returns a formatted string (using code-block syntax highlighting).
   - Leverages existing markdown/code-block formatting so diffs get proper faces.
2. Update =benedict--tool-propose-edit= to build =:body= from the diff content
   (instead of just a summary message).
   - Include the full diff in the body.
   - Keep the summary line at the top (e.g., "Diff: 3 hunks, +12/-8 lines").
3. Add action to open the review buffer:
   ```elisp
   :actions (list (list :label "Open diff"
                        :handler (lambda ()
                                   (pop-to-buffer review-buffer))))
   ```
4. Test: Verify diff rendering with syntax highlighting, button clicks switch buffers.

** Phase 3: Polish & testing
1. Verify marker stability: inline action buttons and diff rendering should not cause
   marker issues when buffers are killed or collapsed.
2. Add property-based tests for action lists (valid/invalid structures, handler invocation).
3. Manual smoke test:
   - Call =propose-edit= tool in chat.
   - Expand the tool call.
   - Verify diff is readable inline with proper syntax highlighting.
   - Click "Open diff" button.
   - Verify review buffer opens without collapsing the tool call.
   - Close review buffer and return to chat; tool call should still be expanded.
4. Check edge cases:
   - Tool with no actions (backward compat).
   - Tool with empty actions list.
   - Handler that throws an error.
   - Multiple action buttons (how do they wrap?).

* Acceptance criteria

- [ ] Generic action button infrastructure is in place and tested.
- [ ] =propose-edit= embeds the full diff in the tool call body with syntax highlighting.
- [ ] "Open diff" button appears next to the tool header and opens the review buffer when clicked.
- [ ] Tool calls without actions still render correctly (backward compat).
- [ ] Markers remain stable when tools have embedded diffs and multiple action buttons.
- [ ] Tests cover: action validation, button invocation, diff rendering, marker stability.
- [ ] Manual smoke test passes (diff visible inline, button works, no UI glitches).

* Open questions / risks

- **Button layout on narrow windows**: If buttons wrap to a new line, how should they be indented?
  → Plan: Inline buttons on header line; if too wide, insert a second line with buttons indented.
- **Handler scope**: Handlers run in the chat buffer; should they have access to the tool item?
  → Plan: Handlers are user-provided lambdas; for now, capture what they need via closure.
  → Future: Consider passing item context if handlers need to cross-reference.
- **Diff size limits**: Very large diffs might bloat the UI. Should we cap/truncate them?
  → Plan: No cap for now; revisit if perf issues arise. Can add a defcustom later.
- **Syntax highlighting in temp buffers**: Current code-block rendering uses a temp buffer;
  confirm it works correctly for diffs.
  → Plan: Verify in Phase 3 smoke test.
- **Concurrent tool actions**: If user clicks an action, can they click another before it completes?
  → Plan: Actions are synchronous for now. Future: add busy flag if needed.
