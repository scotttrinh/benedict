#+TITLE: Plan — Render Simplification Pass
#+DATE: 2025-12-13

* Goal
Reduce rendering complexity and prevent cross-module buffer mutation bugs by tightening the rendering API and consolidating the most common “write + refontify” operations.

* Context
Rendering/streaming currently spans multiple modules (buffer edits in more than one place), and correctness relies on a growing set of marker + sentinel invariants. This increases the chance of regressions like “final completion rewrite clears markdown styling”.

Today, we already have a partial “single writer” split:
- =benedict-chat-render.el= renders tool items and message items, and owns most marker/sentinel behavior.
- =benedict-chat-stream.el= still performs direct buffer edits for streaming deltas (=insert= into the body region).
- There are multiple “replace content region” helpers with overlapping responsibilities (and confusing naming):
  - =benedict-chat--write-message-item-body= (writes =body= region, no font-lock)
  - =benedict-chat--write-message-item-content= (writes =tool-ui= region, no font-lock; name suggests message but used as a general helper)

This plan is about making the boundary explicit and shrinking the number of “ways to write into chat”.

* Constraints / Non-Goals
- Keep the existing “sentinel newline” marker pattern (header/content regions exclude the sentinel newline).
- Keep folding behavior intact (tool folds + message/thinking folds if present).
- No redesign of markdown-mode fontification; only consolidate how we trigger it.
- Maintain Emacs 27.1+ compatibility.

* Proposed Direction (High-ROI Simplifications)
** 1) Single writer rule
- Make =benedict-chat-render.el= the only module that performs buffer mutation for chat output (headers, bodies, tool UI).
- =benedict-chat.el= should manage state and call a small render API.
- =benedict-chat-stream.el= should become a thin “stream state + render calls” module (no direct buffer edits).

** 2) Consolidate body writes + refontification
- Introduce a single helper that:
  - replaces an item body region with text
  - applies =benedict-region-kind= correctly (=body= vs =tool-ui=)
  - updates stable markers (especially =:content-end=)
  - runs =font-lock-flush/ensure= on the affected region (or schedules/throttles this work)
- Replace all call sites that currently do “delete/insert”, “replace + flush/ensure”, or “insert delta directly” with the helper(s).

** 3) Make the render API explicit (small surface area)
- Introduce (or rename existing) internal render entrypoints so other modules don’t need to know marker/sentinel details:
  - =benedict-chat-render--set-item-content= (replace entire content region, then refontify)
  - =benedict-chat-render--append-item-content= (append delta at =:content-end=, then refontify or schedule)
  - =benedict-chat-render--rewrite-item-header= (rewrite header text without disturbing content markers; keep sentinel newline stable)
- Keep higher-level “render an item” entrypoints (message/tool/thinking) in the render file, but make the mutation helpers the only way they update regions after initial render.

** 4) Unify block rendering primitives
- Ensure both message items and tool items use one underlying “render block” primitive.
- Parameterize the block primitive with:
  - content region kind (=body= vs =tool-ui=)
  - header formatting function
  - optional footer / actions insertion

** 5) Reduce marker surface area
- Keep only the markers that must be stable for streaming and updates:
  - header start marker
  - content end marker (stream append target)
- Derive other boundaries when needed via text properties on the item (=benedict-chat-item=) + property-change scanning.

** 6) Optional follow-up: throttle fontification on streaming
- Consider coalescing font-lock work (idle timer / throttled ensure) rather than ensuring every delta synchronously.
- Keep correctness guarantees: the body should be fontified “soon” and always be correct after completion.

* Acceptance Criteria
- All buffer mutations related to chat rendering go through =benedict-chat-render.el=.
- Exactly one helper is responsible for “set message/tool body region text and ensure markdown faces”.
- Streaming completion does not clear markdown-mode styling.
- Existing tests pass: =nix run .#test= and =nix run .#lint=.
- No UI regressions: headers remain stable; streaming inserts into the correct body region; tool blocks still render and update.

* Tentative File/Function Changes
- =benedict-chat-render.el=
  - Add/rename: =benedict-chat-render--set-item-content= (replace + refontify; parameterized by region kind).
  - Add: =benedict-chat-render--append-item-content= (append delta + refontify/throttle).
  - Consolidate/remove: =benedict-chat--write-message-item-body= and =benedict-chat--write-message-item-content= call sites.
  - Extend: block primitive to support both message/tool content kinds.
- =benedict-chat-stream.el=
  - Replace direct =insert= with calls into =benedict-chat-render--append-item-content= (or equivalent).
  - Keep: buffering/throttling policy and stream lifecycle state.
- =benedict-chat.el=
  - Replace direct body replacement logic with render helper call(s).
  - Keep orchestration: state machine, metadata, timers.

* Plan of Attack
1. Identify all buffer mutation call sites outside =benedict-chat-render.el= (start with =benedict-chat-stream.el= and completion rewrite paths).
2. Add/rename render helper(s) in =benedict-chat-render.el=:
   - “replace content region + refontify”
   - “append delta + refontify/throttle”
3. Migrate completion path(s) to use the unified helper (avoid duplicate “delete/insert + ensure” logic).
4. Migrate streaming delta path to use the unified helper (no direct =insert= from stream module).
5. Audit for remaining buffer mutations outside the render layer and migrate incrementally.
6. Run =nix run .#test= and =nix run .#lint=.

* Audit Checklist (Helpful Greps)
- =rg -n "insert \\(propertize|delete-region|replace-region-internal" benedict-chat.el benedict-chat-stream.el=
- =rg -n "font-lock-(flush|ensure)" benedict-chat.el benedict-chat-stream.el=
- =rg -n "write-message-item-(body|content)" -S=

* Risks / Notes
- Marker behavior is subtle (insertion-type, sentinels). Changes should be incremental and covered by existing integration tests.
- Keep the “single writer” boundary strict to avoid reintroducing split responsibilities.
