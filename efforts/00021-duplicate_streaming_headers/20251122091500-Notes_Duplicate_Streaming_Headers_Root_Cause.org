#+TITLE: Notes: Duplicate Streaming Headers — Root Cause and Fix
#+DATE: 2025-11-22
#+AUTHOR: Amp

* Problem Statement

Users reported seeing duplicate `[ASSISTANT]` headers when receiving streaming responses:

```
[ASSISTANT]
[ASSISTANT]
## Analysis

Some content here

[ASSISTANT]
```

This occurred consistently with streaming responses, and appeared to bracket message/tool-call bodies rather than appearing once per response.

* Investigation and Discovery

Added instrumentation logging to key functions:
- `benedict-chat--ensure-streaming-message`
- `benedict-chat--record-message`
- `benedict-chat--insert-message`
- `benedict-chat--handle-provider-success`

The logs revealed that **`handle-provider-success` was being called twice** per streaming response:

1. First call: `streaming-msg-exists=YES` → Path A (update existing message)
2. Second call: `streaming-msg-exists=NO` → Path B (insert new message, causing duplicate header)

This happened because `streaming-reset` (called at line 1912 in `handle-provider-success`) cleared the global `benedict-chat--streaming-message` variable, but by that time the first callback had already captured it. The second callback found it `nil`.

* Root Cause

Located in `benedict-chat.el` lines ~2004-2011 in `benedict-chat--start-dispatch`:

```elisp
(benedict-provider-dispatch
 request
 :on-success (lambda (result)
               (when (buffer-live-p buffer)
                 (with-current-buffer buffer
                   (benedict-chat--handle-provider-success result))))
 :on-complete (lambda (result)
                (when (buffer-live-p buffer)
                  (with-current-buffer buffer
                    (benedict-chat--handle-provider-success result))))
```

**Both `:on-success` and `:on-complete` callbacks were calling the same function.**

According to the provider API documentation:
> ON-COMPLETE: optional final callback for streaming providers; when nil the provider should fall back to ON-SUCCESS.

This means:
- For streaming responses: `:on-complete` is the final callback
- For non-streaming responses: `:on-success` is called

But the implementation was calling the same handler for both, resulting in duplicate processing.

* Solution

Removed the `:on-complete` callback, relying solely on `:on-success`. This works because:

1. Non-streaming responses call `:on-success` once
2. Streaming responses also call `:on-success` once (after the stream ends)
3. The `:on-delta` callback handles streaming chunks separately

Alternative approach (not taken): Could have added a guard flag to prevent double-processing:

```elisp
(let ((success-called nil))
  :on-success (lambda (result)
                (when (and (buffer-live-p buffer) (not success-called))
                  (setq success-called t)
                  (benedict-chat--handle-provider-success result)))
  :on-complete (lambda (result)
                 (when (and (buffer-live-p buffer) (not success-called))
                   (setq success-called t)
                   (benedict-chat--handle-provider-success result))))
```

But removing the duplicate callback is cleaner.

* Verification

After removing `:on-complete`:
- Streaming responses show a single `[ASSISTANT]` header at the start
- Content streams in correctly
- No duplicate headers bracket the message body
- Tool calls render correctly below the message

* Code Changes

Edited `benedict-chat.el`:
- Line ~2008: Removed the `:on-complete` lambda entirely
- Kept `:on-success`, `:on-error`, and `:on-delta` callbacks

* Follow-up

Removed all debug logging added during investigation:
- `DEBUG: record-message called...`
- `DEBUG: insert-message called...`
- `DEBUG: ensure-streaming-message called...`
- `DEBUG: handle-provider-success ENTRY...`
- `DEBUG: handle-provider-success Path A/B...`

These can be removed in a final cleanup pass or left for future debugging sessions.

* Root Cause Analysis Summary

**Why it happened**: Cargo-cult callback registration — both `:on-success` and `:on-complete` were defined even though only one should be used per request type.

**Why it wasn't caught earlier**: Streaming and non-streaming code paths were working (because `streaming-msg` was captured before reset), but the second callback would always fire after reset, creating a spurious duplicate.

**Why logs made it obvious**: The sequential log entries showing two `handle-provider-success ENTRY` calls made the duplicate callback registration immediately visible.
