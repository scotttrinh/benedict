#+TITLE: Notes: Subagents and Environment Bootstrapping
#+DATE: 2025-11-25

* Context
These notes capture early thinking on two related topics:
- How Benedict should model and handle “subagents” (specialized helpers that the main agent delegates work to).
- What “environment details” we should send with the initial and subsequent requests to help the model orient quickly inside an Emacs project.

These are framing notes and questions, not a commitment to an implementation.

* Subagents
** Working definition
- A subagent is a named, constrained helper that the main Benedict agent can invoke for a bounded task (e.g., “search and summarize”, “propose edits”, “run tests”), possibly with its own profile and autonomy limits.
- Subagents may share the same underlying model as the primary agent, but with different system prompts, tools, and budgets.

** Design options
- Single-process, multi-role: treat subagents as profiles with stricter autonomy and narrower tool access, orchestrated by Benedict rather than the provider.
- Tool-call-based: expose “invoke-subagent” as a tool where the model chooses a role and budget; Benedict turns that into a structured call with clear logging and approvals.
- Data-only subagents: allow the main agent to ask for pre-baked “views” (project search, file lists, test status) that look like subagents from the model’s perspective but are implemented as tools.

** Safety and UX considerations
- Budgets: each subagent should inherit global and profile-level limits (turns, time, tokens) but be able to tighten them.
- Approvals: user should see which subagent is acting, what it intends to do, and how far it is allowed to go before needing renewed approval.
- Observability: logs and UI should make it obvious when work is being done by a subagent vs. the main agent (helpful for debugging and trust).
- Failure modes: decide how errors propagate back (e.g., subagent fails → main agent summarizes and asks user how to proceed).

** Questions to revisit
- When does explicit “subagent” modeling add value over a single, carefully-prompted agent with tools? (i.e., are we solving user problems or just mirroring provider features?)
- Do subagents need persistent state across sessions, or are they purely ephemeral per thread or per request?
- How should subagent activity surface in the UI? Separate buffers, folds, or inline annotations in the main chat?
- Should users be able to define their own subagents declaratively (profiles + tools + limits), or should Benedict ship a small, curated set?
- How do we avoid overwhelming users with autonomy controls (global, profile, subagent) while still staying safe-by-default?
- How do subagents interact with the layered autonomy work (Phase 6.1)? Do we need an explicit budget composition story?

* Environment details & telemetry
** First-pass payload ideas (initial request)
- Project identity: project root path (redacted in logs as needed), VCS status (branch name, dirty/clean).
- Code shape: limited-depth, limited-count file tree focused on “interesting” files (current buffer, neighbors, major languages).
- Active context: major mode, current profile, open buffer names, narrowed region or selection when applicable.
- Task context: high-level todo state, including “current todo”, a short list of incomplete items, and the most recently completed item (pulled from Flywire or buffer-local todo metadata when available).
- Capabilities: model name, provider, tools available, and whether streaming and tool calls are enabled.

** Subsequent message telemetry
- Context window facts: approximate total tokens used, estimated headroom, and any internal truncation decisions.
- Session constraints: active autonomy limits (time, turns, tokens) and whether the loop is currently paused or free-running.
- UI context: open buffers relevant to the current exchange (e.g., files recently visited in this thread).
- Light “spend” hints: approximate cost counters (per-thread, per-project) scoped to avoid privacy surprises.
 - Todo evolution: changes to the “current todo”, newly completed items, and any new todos created by the agent itself, so the model can keep plans aligned with the user’s task list.

** Design questions
- What is the minimal environment payload that meaningfully improves the model’s planning without leaking unnecessary user data?
- How frequently should we resend environment details to avoid drift (e.g., files changed on disk, project root moved) without burning tokens?
- How much of this should be configured per user / per project (e.g., opt out of file lists, cap file tree depth)?
- Should environment telemetry be model-facing only, or also exposed to users in a human-readable “what the agent sees” panel?
- How do we avoid the model overfitting to the telemetry (e.g., treating token budget estimates as hard limits)?
 - How tightly should we couple environment telemetry to a specific todo system (e.g., Flywire) vs. a thin abstraction that can pull from multiple sources (org-mode, project-local todo files, etc.)?
 - What is the right granularity for todo data (full descriptions vs. summarized labels) to keep payloads small but still useful for planning?

* Interplay & sequencing
- Subagents will likely depend on richer environment details to plan effectively (e.g., choose which files or tools to delegate to).
- Environment bootstrapping can ship in a minimal form earlier (around the existing project context work and agent loop) and then be refined to support more sophisticated subagent behavior.
- The Roadmap update captures these as “Future” work items that can be pulled into post-1.0 planning once the core chat, tools, and persistence features are solid.
