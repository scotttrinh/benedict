#+TITLE: Notes — History, Branching, and Compaction
#+DATE: 2025-11-25

* Context
- Capturing design thoughts around history management in Benedict: branching, time-travel, multi-model experiments, and compaction.
- Goal is to shape Phase 7+ roadmap items and future UX around persistence and experimentation.

* Ideas and Directions
** Branching Semantics
- Allow branching at any message: treat each turn as a potential fork point for a new thread.
- Support ephemeral vs. named branches (e.g., quick “what if” vs. long-lived `refactor-auth`).
- Establish a protected mainline per project/thread; experiments must be explicitly merged back.

** Multi-Model Workflows
- Run the same prompt on multiple models in parallel and present responses side-by-side.
- Add an “experiment/tournament mode” that compares answers using simple heuristics (tests, length, style) and/or user choice.
- Associate branches with preferred models (e.g., `perf-gpt-o3`, `docs-gpt-4.1`), merging artifacts rather than raw conversational turns.

** Time-Travel and Checkpoints
- Named checkpoints within a thread (e.g., =pre-bug-xyz=) that can be resumed without destroying future history.
- One-shot “redo from here” that auto-branches when the user wants to ignore a long detour.
- Safe snapshots around risky operations (large refactors, framework upgrades), optionally tied to git commits or worktrees.

** Merging and Reconciliation
- Merge branches via summaries: synthesize a combined narrative instead of concatenating full transcripts.
- Use artifacts (files, diffs, commits) as the ground truth; treat chat history as commentary layered on top.
- Provide conflict views that compare plans between branches and let the user pick or blend outcomes.

** Compaction and Pruning
- Layered history representation: raw transcript → per-segment summaries → high-level “story of this task”.
- Semantic compaction: preserve code and diffs while summarizing repetitive back-and-forth.
- Structural compaction: collapse repeated “fix small bug, rerun tests” cycles into a single summarized node.
- User-level policies per thread: auto-compact older content unless pinned, or keep full history for important threads.
- Preserve non-compacted histories alongside compacted views so we can always “unzip” or “rezip” segments; treat compaction as a reversible view transform, not destructive pruning.
- In the chat buffer, represent compacted chunks with a visible wrapper (e.g., fold/summary node) that can expand to show the full underlying transcript; this lets message history be a first-class, explorable affordance rather than hidden state.

** Task-Centric Views
- Tag history by task/epic so related work can be surfaced even when it spans multiple chat buffers.
- Align timelines with git history (interleave chat turns and commits).
- Add a replay mode to step through how a solution evolved.

** Safety and Contamination Controls
- Context firewalls between branches: opt out of importing content from certain experiments into others.
- Redaction checkpoints when merging/compacting, with helpers for PII or sensitive paths.

* Prior Art to Reference
- Git: branching, worktrees, bisect, interactive rebase as conceptual models.
- IDE/agent integrations: Cursor/Windsurf/Copilot Chat tying chats to files/commits.
- Jupyter/Hex/Deepnote and ML experiment trackers for checkpointing and experiment history.
- Chat and doc tools: ChatGPT’s branching, Perplexity projects, Google Docs/Notion version history.

* Product Questions
- What is the core unit of history: message, episode, task, or commit-linked bundle?
- How explicit should branching be in the UI vs. mostly implicit with lightweight affordances?
- How should merges feel (rare power-user action vs. everyday “apply from this experiment”)?
- How tightly should conversational branches map to git branches/worktrees vs. purely conceptual branches?
- When and how should compaction be automatic, and how do we represent summarized segments so users trust what was preserved?
- How do we keep multi-model experiments ergonomic instead of overwhelming (defaults, per-thread model, experimental branches)?
- What are the default recovery workflows when conversations “go off the rails”, and when should the system suggest branch/checkpoint creation automatically?
