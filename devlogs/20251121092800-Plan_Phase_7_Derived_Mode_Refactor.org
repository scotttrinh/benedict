#+TITLE: Plan: Phase 7 — Derived Mode Refactor & Provider Abstraction
#+AUTHOR: Benedict maintainers
#+LANGUAGE: en
#+OPTIONS: toc:nil num:nil ^:{}

* Summary
Introduce a dedicated, read-only chat major mode that keeps full control over the entire buffer layout while delegating message-body rendering and styling to markdown-mode’s fontification machinery. This plan removes the "lite" markdown-mode logic, cleanly separates message content from surrounding UI regions, and abstracts buffer updates away from the provider layer so providers become stateless dispatchers while the chat mode manages all display concerns.

* Current State

** Architecture Issues
- =benedict-chat-mode= is a special-mode, which provides minimal UI infrastructure.
- Chat rendering is tightly coupled to message insertion; providers are aware of buffer updates and call =benedict-chat--*= functions directly.
- Fontification (bold, code, headings) is done via crude regex-based text properties, not leveraging Emacs' font-lock system.
- No syntax highlighting in code blocks despite having language information.
- Marker/overlay stickiness is fragile, causing errors when streaming into complex message structures.

** What Works Well
- Message history tracking in =benedict-chat--messages= (plist list, newest first).
- Per-message UI state (thinking blocks, tool calls, spinner state).
- Context slices and compose buffer integration.
- Provider dispatch infrastructure (async callbacks).

* Goals

1. **Use markdown-mode for message regions** while keeping a dedicated chat major mode:
   - Robust fontification (headers, emphasis, code, links) via markdown-mode’s font-lock.
   - Syntax highlighting in fenced code blocks (Python, Bash, etc.).
   - Message bodies feel like read-only markdown-mode regions.
   - Chat mode retains full control over non-message regions (headers, separators, tool UI).

2. **Decouple providers from rendering**:
   - Providers return structured data (messages, tool calls).
   - Chat mode receives and buffers this data.
   - Chat mode drives all buffer updates, marker management, and UI state.
   - Providers are stateless; they don't call =benedict-chat--*= functions.

3. **Remove "lite" markdown-mode logic**:
   - Rely on markdown-mode's full font-lock infrastructure instead of custom regex patterns.
   - Delete custom markup-hiding overlays where markdown-mode's `invisible` property suffices.
   - Use markdown-mode's existing code block detection for syntax highlighting.

4. **Improve marker/overlay lifecycle management**:
   - Use correct stickiness for streaming regions (front-non-sticky start, rear-sticky end initially).
   - Flip stickiness after closing sections to avoid accidental region inversions.
   - Audit all timers to guard with buffer liveness checks.

* Implementation Plan

**Region Model & Read-Only Invariants**

Define a single text property, =benedict-region-kind=, that classifies each span of the chat buffer:
- =body=: message content that should be rendered as markdown (assistant/user/system messages).
- =header=: message headers, timestamps, model names, separators.
- =tool-ui=: structured tool call UI and results (non-markdown regions with richer widgets).
- =system=: any global system/status banners.

Invariants:
- The entire chat buffer is read-only by default; user editing happens via explicit “fork/edit” affordances, not direct modification.
- Only =benedict-region-kind 'body= regions participate in markdown-mode fontification.
- Non-body regions (header/tool-ui/system) use custom faces, overlays, and display properties without interference from markdown-mode’s font-lock.

## Phase 7.2: Major Mode & Region Integration

### Define =benedict-chat-mode= (read-only chat mode)
```elisp
(define-derived-mode benedict-chat-mode special-mode "Benedict-Chat"
  "Major mode for Benedict chat buffers."
  (setq buffer-read-only t)
  (setq-local benedict-region-kind-property 'benedict-region-kind)
  (setq-local word-wrap t)
  (setq-local truncate-lines nil)
  ;; Enable markdown-mode fontification for body regions.
  (benedict-chat--enable-markdown-fontification-in-body))
```

### Markdown Integration for Body Regions

Re-use markdown-mode’s internals (syntax-propertize, font-lock keywords, code-block highlighting) without changing the major mode:
- Borrow =markdown-syntax-propertize-function= and =markdown-mode-font-lock-keywords= into chat-local variables.
- Enable =markdown-fontify-code-blocks-natively= in chat buffers.
- Ensure only =body= regions are passed through markdown’s font-lock; other regions are explicitly excluded.

### Custom Font-Lock Extension
Extend font-lock to constrain markdown-mode fontification to =body= regions and skip everything else (metadata, role tags, timestamps, tool UI):

```elisp
(defun benedict-chat--extend-region-body-only (start end)
  "Extend font-lock region, restricting markdown to body regions.
Non-body regions are marked with the `benedict-region-kind' text property."
  (save-excursion
    (save-match-data
      (let ((new-start start)
            (new-end end))
        ;; Move START backward to the beginning of the current body run.
        (goto-char start)
        (while (and (> (point) (point-min))
                    (eq (get-text-property (1- (point)) 'benedict-region-kind)
                        'body))
          (backward-char))
        (setq new-start (point))

        ;; Move END forward to the end of the current body run.
        (goto-char end)
        (while (and (< (point) (point-max))
                    (eq (get-text-property (point) 'benedict-region-kind)
                        'body))
          (forward-char))
        (setq new-end (point))

        (cons new-start new-end))))))

(add-hook 'font-lock-extend-region-functions
          #'benedict-chat--extend-region-body-only nil t)
```

This mirrors the guide's Strategy 3 (Font-Lock Extensions), keeping the mode simple while allowing markdown-mode to do the heavy lifting inside body regions only.

## Phase 7.3: Streaming Integration (JIT-Lock First)

Streaming remains important, but we defer complex throttling/timer machinery to a later phase.

### Streaming Helpers

- Keep streaming logic factored (e.g., =benedict-chat-stream.el=) so providers send deltas to a small API.
- For each delta:
  - Insert the chunk at the current message’s =content-end= marker.
  - Let JIT-lock/markdown-mode handle fontification lazily.
  - Optionally, if under-fontification is observed, call =font-lock-flush=/=font-lock-ensure= on the new region only.

### Responsiveness Considerations

- Rely on JIT-lock’s built-in coalescing and idle timers to keep Emacs responsive while agents stream.
- Design the streaming helpers so that a future “Phase X: Throttled Streaming” can add timers/queues without changing provider callbacks or the region model.

## Phase 7.4: Provider → Chat Interface

### New Provider Callback Signature
Providers no longer invoke =benedict-chat--*= functions. Instead, they emit structured data:

```elisp
(funcall on-delta :message-id mid
                  :kind 'content-delta
                  :text chunk)

(funcall on-delta :message-id mid
                  :kind 'thinking-delta
                  :text chunk)

(funcall on-complete :message-id mid
                     :kind 'tool-calls
                     :calls [...])

(funcall on-success :messages (final-history)
                    :usage (...))
```

### Chat Mode as Orchestrator
=benedict-chat.el= receives these events and:

1. **For deltas**: Route to =benedict-chat-stream.el= for throttled buffering.
2. **For tool calls**: Create tool call blocks and pause loop.
3. **For completion**: Finalize message, update history, check loop constraints.

No buffer mutations in callbacks; all done via request-response, not side effects.

## Phase 7.5: Rendering Abstractions

### Message Insertion
In =benedict-chat-render.el=:

```elisp
(defun benedict-chat--insert-message (message)
  "Insert MESSAGE (plist) into chat buffer at point."
  (let ((role (plist-get message :role))
        (content (plist-get message :content))
        (metadata (plist-get message :metadata)))
    ;; Insert role tag as a non-body region
    (insert (propertize (format "[%s]\n" (upcase (symbol-name role)))
                        'face 'benedict-chat-role
                        'benedict-region-kind 'header))
    ;; Insert content (markdown-mode will fontify body regions)
    (insert (propertize content
                        'face nil
                        'benedict-region-kind 'body))  ;; Let markdown-mode apply faces
    (insert "\n")))
```

### Streaming Insertion
```elisp
(defun benedict-chat--stream-insert-delta (stream text)
  "Buffer TEXT into STREAM for throttled application."
  (with-current-buffer (benedict-chat--stream-state-buffer stream)
    (let ((state (plist-get (current-buffer) 'benedict-stream-state)))
      (setf (benedict-chat--stream-state-pending-text state)
            (concat (benedict-chat--stream-state-pending-text state) text))
      ;; Reschedule or create timer
      (benedict-chat--throttle-update stream))))
```

### Face Application
After streaming:
```elisp
(defun benedict-chat--apply-buffered-faces (stream)
  "Apply any buffered faces and reset state."
  (with-current-buffer (benedict-chat--stream-state-buffer stream)
    ;; Trust markdown-mode's font-lock
    (font-lock-flush (benedict-chat--stream-state-content-start stream)
                     (benedict-chat--stream-state-content-end stream))
    ;; Ensure faces are applied immediately if needed
    (font-lock-ensure (benedict-chat--stream-state-content-start stream)
                      (benedict-chat--stream-state-content-end stream))))
```

This delegates all fontification to markdown-mode, eliminating custom face logic.

## Phase 7.6: Code Block Syntax Highlighting

### Leverage markdown-mode's Native Support
Markdown-mode already has =markdown-fontify-code-block-natively=, which:
- Detects fenced blocks with language specifiers.
- Creates a temp buffer, runs the language's major mode, applies font-lock.
- Copies faces back to the markdown buffer.

We merely ensure this is enabled:
```elisp
(setq-local markdown-fontify-code-blocks-natively t)
```

No additional work required; markdown-mode handles it.

* Dependencies & Risks

## Dependencies
- Requires =markdown-mode= to be available. Add to =Cask= or test environment.
- Depends on completing Phase 6 (agent loop) first, as this refactor may affect dispatch flow.

## Risks
- **Markdown-mode incompatibility**: Some chat-specific elements (tool calls, thinking blocks) may not render well in markdown-mode. Mitigation: Use =invisible= property or custom overlay properties to hide non-markdown regions.
- **Marker stickiness bugs**: Incorrect stickiness can cause overlays to vanish or invert. Mitigation: Careful testing with markers; audit every marker creation and modification.
- **Performance regressions**: Throttling may improve responsiveness but could introduce subtle timing bugs. Mitigation: Comprehensive tests with rapid delta sequences.
- **Provider refactoring**: Changing provider callbacks is a breaking change. Mitigation: Update all providers and tests in lockstep; no partial rollout.

* Future Improvements (Post-Phase 7)

1. **Custom faces for metadata**: Render role tags, timestamps in a subtle color (e.g., =shadow= face).
2. **Interactive code blocks**: Add copy/run buttons to Bash/Python blocks (like the guide describes).
3. **Indirect buffers for editing**: Allow editing long assistant responses in a full markdown buffer.
4. **Org-mode alternative**: Optionally use =org-mode= instead of markdown-mode for more structure (headings, lists, drawers).
5. **Synchronization**: Keep compose buffer and chat buffer in sync via shared text regions.
