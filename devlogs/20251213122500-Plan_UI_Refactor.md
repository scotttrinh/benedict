Implementation Plan: Benedict Chat UI Refactor (Polished, Section-Based)

## 0. Goal

Refactor Benedict’s chat buffer into a highly scannable, structured, interactive UI while preserving the existing runtime model:

- Underlying data: `benedict-chat--messages` (history), assistant streaming state, tool calls/results, per-message `:metadata` (provider/model/latency/usage), and tool UI (`:ui` with `:header`, `:body`, `:actions`).
- Current rendering constraints: marker-backed insertion for streaming (`benedict-chat-render--append-item-content`), body-only markdown fontification (`benedict-chat-mode`), and fold overlays (`benedict-chat-fold`).

The UI should “feel like Magit”: stable navigation, predictable folding, strong visual hierarchy, and clear separation between content vs. metadata.

## 1. Non-Goals

- No changes to provider/network layer semantics.
- No change to the compose buffer workflow (only update appearance if needed for consistency).
- No bespoke markdown parser; continue to rely on `markdown-mode` for body rendering.
- No forced GUI-only UI; everything must degrade cleanly in terminal Emacs.

## 2. Data We Display Today (Anchor for the Refactor)

Each chat “turn” can include:

- User message: plain text in buffer; not streamed; minimal metadata.
- Assistant message: streamed markdown body; header includes provider/model/elapsed/usage; may include an “empty response” placeholder; may include error state.
- Tool calls: `:tool-calls` on the assistant message, each call has `:id`, `:name`, `:arguments`.
- Tool blocks (UI): rendered as foldable header + body, with optional action buttons; status changes (`in-progress` → `success`/`failure`).
- Thinking blocks: folding infrastructure exists; rendering needs to be brought up to parity.

## 3. Architectural Decision: Keep Marker-Backed Streaming, Add `magit-section` Structure

We keep the existing marker/overlay patterns for correctness under streaming and incremental updates, but adopt `magit-section` to standardize:

- Folding and visibility toggles (TAB, S-TAB, etc.).
- Navigation between blocks/sections (`n`/`p`, jump-to-next error/tool, etc.).
- Clear structural hierarchy (conversation → turns → sub-blocks).

This implies: sections are the “frame” and markers remain the “insertion anchors”.

### 3.1 Dependencies

- `magit-section`: structural UI (required for the refactor).
  - Packaging: add to `Package-Requires` and `Eask` so it is always available.
- `svg-lib`: optional-but-preferred badges in GUI; always provide a text fallback.
- `markdown-mode`: body fontification (already in use).

## 4. Visual Language (“Polished” Rules)

### 4.1 Badges (SVG + fallback)

Badges are for metadata/state, never for content.

Badge classes:

- Role: `USER`, `ASSISTANT`, `SYSTEM`, `TOOL`.
- State: `SENDING`, `STREAMING`, `DONE`, `ERROR`, tool status (`RUNNING`/`SUCCESS`/`FAILURE`).
- Context: provider/model, tool id, call id (when useful), file paths (only when already known).

Implementation notes:

- GUI: `svg-lib-tag` “pill” badges (rounded corners, consistent padding).
- TTY fallback: propertized text (e.g., inverse-video or box-like faces).
- Keep badges in fixed-pitch regions so alignment stays stable.

### 4.2 Typography

- Headers/metadata rows: fixed-pitch.
- Message bodies: variable-pitch (but code blocks/diffs remain fixed-pitch via face remapping and markdown code faces).
- Tool output “cards”: use faces with background and `:box` padding instead of ASCII borders.

### 4.3 Alignment & Density

- Prefer a single header line per block (role + badges + key metadata).
- Optional right-aligned metadata (elapsed, tokens/cost) using `(space :align-to ...)`.
- Keep empty lines intentional: one blank line between top-level blocks, no extra noise.

### 4.4 Fringe Bars (Optional, Configurable)

We can add a “fringe ownership bar” for quick scanning (enabled by default, opt-out via defcustom):

- Implemented with overlays spanning the message block (not text properties) to remain stable under streaming.
- One bar per top-level block; color indicates role/state (user, assistant streaming, assistant done, tool, error).
- Must be disabled automatically in terminals / when fringe isn’t available.

## 5. Section Hierarchy (Magit-Section)

Root: Conversation

- Turn section (grouping):
  - User block
  - Assistant block
    - Thinking subsection (collapsed by default)
    - Tool call/result subsections (each collapsed by default; expand on failure)
    - Final response body (expanded by default)

Note: Benedict’s internal history is message-based, not turn-based. The renderer should build turns by walking `benedict-chat--message-history` and grouping “user + following assistant (+ tools)”.

## 6. Rendering & Update Strategy (Streaming-Safe)

### 6.1 Initial Render / Refresh

- Implement a single “render tree” function that can rebuild the buffer from `benedict-chat--messages`.
- Maintain an index from stable item IDs (message/tool) → section objects/markers so updates can be localized.

### 6.2 Incremental Updates

Support the existing live behaviors without a full refresh:

- Assistant streaming deltas: append into the assistant body region marker and extend the containing section boundary.
- Telemetry tick updates: rewrite only the assistant header row (existing `benedict-chat--refresh-message-header` pattern).
- Tool status updates: rewrite tool header and tool body (existing tool update flow), and adjust folding defaults (e.g., auto-expand on failure).

### 6.3 Auto-Scroll Behavior

- Default: keep point at end when user is already at end.
- If user scrolls up, do not yank point back down; provide a quick “jump to latest” command.

## 7. Work Items (Phased)

### Phase A — Foundation (no visible regressions)

- Add a new section-aware renderer module (keep the existing renderer functional during transition).
- Define/standardize the “block types” and their section keys (message, tool, thinking, etc.).
- Ensure markdown body-only fontification still works (honor `benedict-region-kind` boundaries).

Acceptance:
- Streaming continues to append without marker drift.
- Existing tests for streaming/tool toggles still pass.

### Phase B — Magit-Section adoption

- Create `benedict-chat-ui-mode` derived from `magit-section-mode` (still read-only).
- Implement section insertion helpers for: turn, message, tool, thinking.
- Replace ad-hoc tool toggles with section toggling where possible (keep buttons only for “actions”, not folding).

Acceptance:
- `TAB` toggles tool/thinking subsections.
- `n`/`p` moves between blocks reliably.

### Phase C — Badges + visual polish

- Add badge renderer: `benedict-chat-ui--badge` (SVG + fallback).
- Update headers to use badges instead of raw `[ROLE]` labels.
- Add “tool status badge” and refine tool header layout (status + name + summary + actions).
- Tool subsections: show terse metadata in the folded header; when unfolded, render that metadata as a structured block (table/card) between the header and the tool body.
  - Example (file tools): folded header shows basename (e.g., `foo.el`), unfolded metadata block includes full relative path plus other call fields.
  - Metadata source: tools provide ordered key/value pairs in two UI fields (concise vs detailed); renderer chooses which to display based on fold state and available space.

Acceptance:
- Works in GUI and TTY.
- No unreadable color combos on vanilla themes (faces inherit from `success/warning/error/shadow` where possible).

### Phase D — Thinking parity

- Render thinking blocks as first-class subsections with consistent folding.
- Ensure thinking content is clearly labeled and de-emphasized by default.

Acceptance:
- Thinking can be toggled without affecting body fontification or tool sections.

### Phase E — Navigation & QoL

- Commands: jump to last assistant, next/prev tool, next error, jump to latest.
- Consistent keybinding story under `benedict-keymap-prefix` and within the chat buffer.

Acceptance:
- Navigation is discoverable (`?`/help buffer optional).

## 8. Acceptance Criteria (Overall)

- Performance: streaming and tool updates remain smooth (no full-buffer re-render per delta).
- Correctness: no marker drift; toggling never corrupts content; edits remain read-only.
- Clarity: headers are scannable; tool details are not noisy; failures are obvious.
- Compatibility: Emacs 27.1+; TTY fallback is functional.

## 9. Verification Plan

- Run tests: `nix run .#test` (add new ERT tests only where existing suites already cover UI primitives).
- Run lint: `nix run .#lint`.
- Manual QA (fake provider):
  - Stream an assistant response and confirm header updates + auto-scroll behavior.
  - Trigger at least one tool call success and one failure; confirm folding defaults and visibility.

## 10. Open Questions / Decisions to Lock In

- Do we add `magit-section` as a hard dependency in `Package-Requires`, or load it opportunistically with a fallback to current overlay folding?
  - Decision: make it an explicit dependency (add to `Package-Requires` and `Eask`).
- Should the fringe bar be enabled by default, or opt-in via a defcustom?
  - Decision: enabled by default, opt-out via a defcustom.
- Do we treat tool “body” as markdown (with fenced code blocks) or as a distinct fixed-pitch region with custom faces only?
  - Proposal: allow tools to render into a buffer and return a reference, so the tool section can show a slice + “show more”, preserving rich formatting from that buffer (potentially even a vterm-like view).
  - Decision: persist tool output by snapshotting at serialization-time (not eagerly); restored sessions render the snapshot (no attempt to resurrect the original live buffer).
  - Decision: UI contract supports either `:body` string or a buffer-backed view (`:body-buffer` + optional `:body-range`), with tools free to remain string-only.
  - Decision: allow referencing any buffer type for buffer-backed tool UIs; rely on display-size capping by default and track any future “unsafe/gate” needs as they arise.
  - Decision: buffer-backed tool UIs are static-at-insert for now (copy the rendered slice once; no live refresh).
- For tool metadata: do we standardize a generic metadata schema (e.g., `:meta` key/value rows on `:ui`), or derive it per-tool from `:tool-call` arguments + tool output?
  - Decision: tools push ordered key/value pairs into two metadata keys (“concise” and “detailed”); renderer selects and truncates based on fold state and available space, treating order as priority.
