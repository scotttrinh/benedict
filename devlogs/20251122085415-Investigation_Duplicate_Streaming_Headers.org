#+TITLE: Investigation: Duplicate Streaming Headers
#+DATE: 2025-11-22
#+AUTHOR: Amp

* Problem
User reports seeing duplicate `[ASSISTANT]` headers at the beginning of streaming responses:
```
[ASSISTANT]
[ASSISTANT]
## Analysis
...
[ASSISTANT]
```

The user is using Vercel provider with streaming enabled. There's also an empty `[ASSISTANT]` block at the very end.

* Initial Analysis

Looking at the streaming flow:

1. **First delta arrives** → `handle-provider-delta` → `ensure-streaming-message`
   - Creates a message record via `record-message` which calls `insert-message`
   - `insert-message` inserts `[ASSISTANT]\n` header (first one)
   - Then `stream-init` sets up markers to point after the header

2. **Streaming deltas flow** → `stream-insert-delta` appends text after `:content-end` marker
   - This should be the content (## Analysis)
   - Correct so far

3. **At end of request** → `handle-provider-success` → `streaming-reset`
   - Calls `stream-init` again
   - But this just reinitializes markers, shouldn't insert anything

* Hypothesis: Possible Causes

** Theory A: `record-message` called twice
- If `ensure-streaming-message` or some other code path calls `record-message` or `insert-message` twice
- Could result in two `[ASSISTANT]` headers
- But why would it be called a second time if the `unless` guard at line 1839 should prevent re-entry?

** Theory B: `insert-message` inserting at wrong position
- Maybe `insert-message` is being called with `(point-max)` at a time when there's already content
- Or markers are pointing to the wrong locations

** Theory C: Provider-specific issue
- Vercel provider might be calling the delta handler twice with initial metadata
- Or there's something in the curl/HTTP layer that's duplicating events

The cleanest approach:
1. Add a `:debug` flag to `benedict-provider-vercel--state-create` to track requests
2. In `benedict-chat--handle-provider-delta`, log the message-id, kind, and text length
