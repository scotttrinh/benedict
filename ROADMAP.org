This roadmap is a living plan that breaks down the aspirational vision in README.org into concrete phases, tasks, and acceptance criteria.

* Guiding Principles
- Emacs-first: buffers, faces, keymaps, and established UIs (Magit, diff/ediff, compile)
- Safe-by-default: preview all writes; explicit approvals; provenance logging
- Provider-agnostic: minimal interface; feature flags; degrade gracefully
- Progressive delivery: ship useful slices early; keep APIs stable where possible
- Testable: ERT/Buttercup with recorded fixtures; network tests opt-in

* Version Targets
- v0.1.0 (Pre‑alpha): Echo provider, chat buffer, minimal tool registry, diff preview
- v0.2.0 (Alpha): First real provider (non-streaming), basic approvals, project context
- v0.3.0 (Alpha+): Streaming support, markdown/code rendering polish, cancellation
- v0.4.0 (Beta): Tooling: search/apply-diff/magit actions; provenance; profiles
- v0.5.0 (Beta): Multi-provider registry; local endpoints; robust errors
- v1.0.0: SQLite-backed persistence/history, UX polish, extensibility API, docs/CI/MELPA release

* Phase 0 — Spike & Design (docs only)
Deliverables:
- Package namespace, defgroup/defcustom plan, faces and keymap conventions
- Provider interface sketch; tool registry schema and approval states
- Streaming plan (url-retrieve vs make-process + curl -N/SSE)
- Security posture: key management via auth-source; redaction helpers; logging policy
Acceptance:
- README.org and this ROADMAP.org merged; example snippets compile in isolation

* Phase 1 — Package Skeleton & Echo Provider [DONE]
Tasks:
- Create benedict.el with autoloads, defgroup, faces, keymaps, error types
- benedict-chat-mode: buffer creation, message rendering (simple), send command
- benedict-mode minor mode: ask region/defun; echo transform locally
- Tool registry (skeleton): register, list; call with plist args; approval stubs
- Persistence stub: in-memory store; lay down SQLite schema (sqlite.el), migrations scaffold
Acceptance:
- M-x benedict-chat opens a buffer; typing and sending creates an echo response
- benedict-ask-region sends region and shows response; no network required
- Tools can be listed and invoked; approval UI shows a placeholder dialog

* Phase 2 — First Real Provider (non-streaming) [DONE]
Tasks:
- OpenRouter backend using url-retrieve; error handling; retries with backoff
- Auth integration: auth-source search; env var fallback; redact in messages
- Chat buffer roles: user/assistant/system; retry last; copy to kill-ring
- Non-streaming rendering; code fences; basic markdown-lite font-lock
- Project context collection: region/defun/buffer; project.el root; simple templates
- Manual testing plan: document credential setup, buffer commands, and checklist for exercising a real OpenRouter request
Acceptance:
- Users can configure endpoint and model, send prompts, and receive full responses
- Per-project settings respected; context preview before send togglable
- Errors are surfaced inline with actionable messages

* Phase 3 — Streaming & Rendering [DONE]
Tasks:
- SSE via make-process + curl -N or provider-native streams; chunk parser
- Incremental rendering with throttling; cursor stability; cancel/timeout
- Introduce typed chat items (message, thinking, tool-call, tool-result, plan, status) with per-item markers and renderers; markdown-lite applies only to message-like content
- Code block rendering; language detection from fences; actions: copy/apply-snippet; folding overlays and buttons for thinking/tool/plan blocks
- TODO: Fenced code blocks reuse per-language prog-mode font-lock (indirect/narrowed buffer) and copy faces back into chat buffers
- Modeline status: tokens (if available), duration, provider name; provider/model segment is clickable and will open a model picker menu (stub in Phase 3, wired up when provider registry/multi-model support lands)
- UI tests: drive typed item rendering and folding/buttons using the fake provider with scripted streaming events, tool calls, and plan updates; assert buffer layout and text properties in ERT/Buttercup tests
Acceptance:
- Streaming feels smooth; cancel works reliably; no UI stutter on large outputs
- Typed items render as distinct blocks (messages vs thinking vs tools vs plans); folding and buttons work; copy/apply actions operate on the correct regions
- Code fences font-lock in streaming content; markdown-lite decoration is incremental and does not re-fontify the entire buffer

* Phase 4 — Context & Project Integration [IN PROGRESS]
Tasks:
- Commands: ask region/defun/buffer/project; keymap prefix (default C-c b)
- xref/imenu/treesit context providers; configurable slice sizes; elide large files
- Git context: current branch, staged/unstaged diffs; preview what will be sent
- Profiles: planning/coding/writing/review; system prompts; per-project defaults
Acceptance:
- Context_pack preview shows what will be sent; toggles apply; provider receives slices
- Ask commands aware of region/defun; responses differ by profile

* Phase 5 — Tools & Approvals (OpenCode‑inspired)
Tasks:
- Toolcall protocol: JSON args → plist; schema validation; approval policies: auto/confirm/always
- Built-ins: search_project (ripgrep), propose_edits (unified diff), apply_diff (diff-mode/ediff)
- Approval UI: transient menu + diff/ediff buffer; provenance logged to thread metadata
- Magit actions (safe subset): stage hunks, commit with suggested message; no pushes initially
Acceptance:
- Agent can request search/edit; user sees approvals; diffs apply correctly; Magit reflects changes
- Provenance shows who/what/when with redacted args

* Phase 6 — Multi‑Provider & Local Models
Tasks:
- Provider and model registry, selection, feature flags (tools, images, long contexts)
- Anthropic/OpenRouter; local OpenAI‑compatible (vLLM, llama.cpp server)
- Capability discovery; graceful degradation if a feature is unavailable
- Can assign certain provider/model to certain profiles by default.
Acceptance:
- Switching providers is one command/customize; features adapt without errors

* Phase 7 — Persistence, History, UX Polish
Tasks:
- Thread histories: storage interface with file-per-thread, human-readable format (JSONL/sexp); per-project quick switch; file watchers and after-save hooks for incremental reindex; SQLite deferred to a later release
- Placement: project-local .benedict/ (gitignored) with global fallback under XDG data dir; user-configurable
- Versioning/migrations: per-thread schema version tags; migrate on load/save; refuse to write “newer-than-supported” files
- Snippet library for prompts; message pinning; attachments (files/regions)
- Faces/themes tweaks; customization group tidy; command palette via transient
Acceptance:
- Threads persist across sessions; switching projects restores context; UX feels consistent

* Phase 8 — Extensibility API
Tasks:
- Public APIs: register tools, providers, context providers, prompts, renderers
- Hooks for pre/post-send; transformers; model routing
- Examples and minimal docs for extension authors
Acceptance:
- Third-party package can register a tool and have it show up with approvals

* Phase 9 — Packaging, Docs, Release
Tasks:
- MELPA recipe; package-lint and Checkdoc clean
- CI: ERT/Buttercup; recorded fixtures; byte-compile on matrix of Emacs versions
- User guide and cookbook; GIFs; contribution guide and issue templates
Acceptance:
- Package is installable via MELPA; docs guide a new user from zero to success

* Emacs‑Specific Integrations (Details)
- diff/ediff: unified diff application with hunk-level approvals; ediff-quit behavior tuned to leave buffers clean
- Magit: use transients; avoid raw git shell when a Magit function exists; respect user config
- ripgrep: prefer ripgrep.el/consult-ripgrep; return structured matches; open in occur/grep buffers on demand
- projectile/project.el: default to project.el; support projectile if present; never hard require
- org: org-capture templates for decisions; org-link back to files and lines
- helpful/describe-*: use for doc lookups; attach outputs to chat
- compile/recompile: run commands in compilation-mode; parse errors

* Security & Approvals (Operational)
- Policies: auto (read-only), confirm (project writes, network with file contents), always (cross-project writes, pushes)
- Data boundary preview: display outbound context; redaction helpers (paths, emails, secrets)
- Key management: auth-source first, env next; never write secrets to disk; mask in logs
- Provenance: thread-local log with timestamps, tool names, outcomes; optional commit trailers

* Testing Strategy
- Unit tests (ERT) for providers, tool registry, schema validation
- Integration tests (Buttercup) for chat buffer rendering and approvals
- Recorded responses for providers; golden files for rendering; network tests behind a flag
- UI contracts: ensure keymaps and transients are bound and discoverable

* Risks & Mitigations
- Streaming stability: favor make-process + curl fallback; parse SSE robustly; expose cancel
- Provider drift: capability flags; versioned adapter layer; good error messages
- Performance: throttle rendering; chunk aggregation; avoid blocking redisplay
- Safety: approvals everywhere; tight scopes; no automatic writes without previews

* Future — Subagents & Delegation
Tasks:
- Design a subagent model (roles, tool access, autonomy limits) that layers cleanly on top of the existing agent loop and profiles work.
- Define orchestration and scheduling rules: when and how the main agent can delegate to subagents, and how results are merged back into a single chat narrative.
- Integrate safety and approvals so that subagent actions are visible, attributable, and bounded by per-profile and global budgets.
Acceptance:
- A prototype profile (e.g., “Refactor”) can spin up one or more subagents for search/propose-edit tasks, with their activity clearly surfaced in the UI and logs, and all work still respecting existing autonomy constraints.

* Future — Environment Telemetry & Bootstrapping
Tasks:
- Define a minimal, privacy-conscious “environment payload” for the initial request (project root metadata, limited-depth file lists, active buffers, todo overview, provider/model capabilities).
- Add lightweight, per-message telemetry (context window headroom, active profile, autonomy limits, approximate spend, and coarse-grained todo state such as current todo and recently completed items) that the agent can use for planning and truncation decisions.
- Expose configuration so users can tune or disable environment telemetry per project, and document what information is sent to providers.
Acceptance:
- The agent can describe, in plain language, what environment information (including high-level todo state) it currently sees and how it is using it to plan, and users can adjust or opt out of these details without breaking core functionality.

- M2 (v0.2.0): +2–3 weeks — non-streaming provider + context
