* Purpose

This document describes a full personal agent system built around a
control-plane / worker-plane architecture.

It is intentionally written as a target design, not as a description of the
current implementation of Benedict or any other existing project.  The goal is
to describe the system we want to build if we take the current direction
seriously:

- the user interacts primarily with a long-lived personal assistant agent
- Emacs is the runtime and operating system for the assistant, not merely a
  host integration — the way a shell is Claude Code's runtime
- risky or high-autonomy execution is delegated to isolated worker subagents
- workers are provisioned with bounded capabilities and return structured
  artifact envelopes
- approvals shift away from per-command prompts and toward session-scoped
  capability grants, isolation boundaries, and final-effect confirmation
- the assistant can evolve its own capabilities at runtime by evaluating new
  elisp, installing packages, and redefining its tool surface

This document focuses on:

- high-level system architecture
- subsystem responsibilities and relationships
- capability and permission model
- plugin model (tools, hooks, agent definitions, and behavioral guidance)
- sandbox and execution backend model
- artifact transfer and worker lifecycle
- temporal primitives and event-driven behavior
- self-evolution and runtime extensibility
- representative user flows
- a first vertical slice for implementation


* Design Goals

- Make autonomous agent behavior trustworthy enough to be the default.
- Treat Emacs as the runtime and operating system, not merely an editor
  integration — the assistant is an Emacs process with native access to the
  full Emacs Lisp environment.
- Isolate risky execution from the user's primary environment by delegating to
  sandboxed worker subagents.
- Support composable plugins that bundle tools, hooks, subagent definitions,
  and behavioral guidance — modeled after Claude Code and Codex plugins.
- Treat approvals as capability and boundary decisions, not repetitive
  interruptions.
- Keep the system understandable: every action should have a clear executor,
  capability source, and blast radius.
- Prefer structured artifact envelopes over raw transcripts as the primary unit
  of coordination between the control plane and workers.
- Support temporal primitives (timers, event hooks, idle triggers) so the
  assistant behaves like an always-on assistant, not a chatbot.
- Allow the assistant to evolve its own capabilities at runtime.


* Core Model

The system is organized into two planes:

- *Control Plane*: the personal assistant, running as a long-lived Emacs
  process.  It interprets the user's intent, maintains context and memory,
  brokers permissions and capabilities, coordinates worker subagents, and
  presents results.  Because Emacs is the runtime, the control plane has native
  access to buffers, org-mode, mail, elisp evaluation, and the full editor
  environment.
- *Worker Plane*: isolated execution environments (typically remote VMs) where
  bounded, tool-heavy, risky, or long-running tasks are performed by worker
  subagents.  Workers return structured artifact envelopes to the control
  plane.

The most important design choice is that *the assistant is not the default
place where dangerous execution happens*.  The assistant is primarily an
interpreter, planner, broker, reviewer, and integrator.  When work has a
meaningful blast radius, it is delegated to a worker subagent via a simple
tool call, analogous to how Claude Code's =Agent= tool spawns subagents.


* System Overview

At a high level, the system contains the following subsystems:

- User Interface Layer
- Gateway and Channel Layer
- Personal Assistant Runtime (Emacs process)
- Session and Memory Layer
- Plugin Layer (tools, hooks, subagent definitions, behavioral guidance)
- Capability and Policy Layer
- Worker Subagent Layer (delegation, lifecycle, artifact return)
- Sandbox and Backend Layer
- Artifact and Review Layer
- Temporal Primitives Layer (timers, event hooks, idle triggers)
- Observability and Audit Layer

These subsystems interact as follows:

1. The user interacts with the personal assistant through Emacs or through
   gateways (emacsclient, messaging platforms, etc.) that connect to the
   same long-lived Emacs process.
2. The assistant interprets the request, gathers context from the Emacs
   environment, and decides whether to act directly or delegate.
3. The assistant loads relevant plugins, which provide both executable
   capabilities and behavioral guidance, subject to session policy.
4. If the work is risky, long-running, or execution-heavy, the assistant
   spawns a worker subagent into an appropriate sandbox via a tool call.
5. The worker performs the task in isolation and writes results to a stable
   artifacts directory.  On sandbox teardown, the artifact envelope is
   automatically synced back to the control plane.
6. The assistant reviews, summarizes, applies, or presents the result.
7. The system records the decision path, capabilities used, worker lineage, and
   resulting artifacts.


* Guiding Principles

** Emacs as Runtime

Emacs is the operating system for the assistant, not merely an editor
integration.  The assistant is a long-lived Emacs process with native access to
the full Emacs Lisp environment.  Elisp evaluation is the primary execution
primitive, analogous to how shell execution is Claude Code's primary execution
primitive.

This means:

- Plugins can provide elisp functions that are evaluated and called directly.
- The assistant can extend its own capabilities at runtime by defining new
  functions, advising existing ones, or installing packages.
- All Emacs subsystems (org-mode, magit, mail, project.el, etc.) are natively
  accessible, not wrapped behind a separate integration layer.

** Separation of Meaning and Execution

The assistant owns meaning.

- It interprets user intent.
- It decides which capabilities are relevant.
- It determines whether work should be direct or delegated.
- It synthesizes results from multiple workers.

Workers own execution.

- They carry out bounded tasks.
- They operate inside constrained sandbox environments.
- They return structured artifact envelopes.

This separation makes autonomy safer and easier to reason about.

** Delegation as a Subagent Primitive

Task delegation should be modeled as a simple tool call that spawns a worker
subagent into a sandbox, analogous to Claude Code's =Agent= tool or Codex's
subagent spawning.

The control plane invokes a tool like:

#+begin_example
(benedict-spawn-worker
  :task "Fix the failing test in auth-middleware"
  :backend :remote-vm
  :capabilities '(project-read project-write project-execute)
  :repo "/path/to/repo"
  :artifacts-dir "/artifacts/worker-001/")
#+end_example

The worker runs autonomously in its sandbox.  When it finishes (or the sandbox
is torn down), the artifact envelope is synced back to the control plane
automatically via a lifecycle hook, regardless of whether the control plane
wants to incorporate the results.  This ensures artifacts are never lost to a
transient sandbox.

Safety relies on:

- isolation boundaries (the sandbox itself)
- capability scoping (what the worker is allowed to do)
- session policies
- artifact review before host mutation

Approval prompts are reserved for:

- granting broad new capabilities
- crossing boundaries
- performing identity-bearing or irreversible actions

** Capability-Oriented Permissions

The system should grant capabilities, not merely individual tool calls.

Examples of capabilities:

- read project files
- write project files
- run shell commands in sandbox
- access outbound network
- read org nodes
- update org nodes
- draft email
- send email
- inspect buffers
- mutate host editor state

Capabilities are granted to sessions or workers and consumed by plugins and
runtime actions.

** Plugins as the Unit of Composition

A plugin is a single package that bundles both executable power and behavioral
guidance.  This follows the model established by Claude Code plugins and Codex
plugins, rather than splitting "skills" (behavior) from "plugins" (power) as
separate concepts.

A plugin may include:

- elisp functions (tools callable via eval)
- capability declarations
- hooks and event triggers
- subagent/worker definitions and profiles
- prompt instructions, workflows, and heuristics
- schemas for invocation
- backend compatibility metadata

In an Emacs environment, the distinction between "executable tool" and
"behavioral guidance" is especially fluid because elisp packages can include
both functions and customization variables, and the assistant can evaluate and
extend them at runtime.

Examples of plugins:

- =org=: org node lookup, capture, refile, agenda, state changes, and
  org-specific planning heuristics
- =magit=: diff, commit history, stage/unstage, commit drafting, and
  git workflow guidance
- =project=: project roots, file sets, symbol maps, search, and coding
  conventions
- =mail=: thread inspection, draft composition, and triage workflows
- =coding=: coding worker profiles, test/build loop heuristics, and
  artifact review guidance

** Artifacts Over Transcript

Workers should communicate upward through structured artifact envelopes:

- patch sets (git format-patch)
- command logs and traces
- test results and build logs
- structured summaries
- open questions
- review notes

The system should avoid relying on long raw transcript concatenation as the main
merge or review surface.


* Top-Level Components

** User Interface Layer

The UI layer is the user-facing surface of the system for rich interactive
work.  In the primary design, Emacs is the main interface, but the architecture
should not depend on Emacs as the only future interface.

Responsibilities:

- conversation view
- task and worker status
- context inspection
- approval and capability grant dialogs
- artifact review
- diff browsing
- history and branch navigation
- notifications

The UI should present a coherent experience where the user feels like they are
talking to one assistant, even when multiple workers are active underneath.

** Gateway and Channel Layer

The assistant always runs within a long-lived Emacs server process.  Gateways
are alternate entry points that connect to that process — they do not run
separate assistant instances.

This layer is responsible for:

- accepting inbound requests from multiple channels
- authenticating and identifying users
- mapping channel messages into the assistant's shared session model
- attaching channel metadata and reply routes
- delivering responses, updates, and notifications back to the originating
  channel
- enabling handoff from low-bandwidth interfaces to richer review surfaces

Examples of gateways include:

- direct Emacs invocation (the primary interface)
- =emacsclient= into the long-lived Emacs server (local or remote)
- terminal or web clients
- Slack, Discord, WhatsApp
- webhook or automation triggers

All gateways talk to the same Emacs process and session model.  A gateway is
an alternate surface over shared assistant state, not a separate assistant.

** Personal Assistant Runtime

The personal assistant runtime is the heart of the control plane.  It is an
Emacs process — Emacs is the runtime, the way a shell is Claude Code's runtime.

Responsibilities:

- interpret user requests
- maintain conversational and task continuity
- activate plugins and bind capabilities
- gather context from the Emacs environment (buffers, org, project state, etc.)
- evaluate elisp as the primary execution primitive
- decide whether to act locally or delegate to a worker subagent
- spawn, monitor, and integrate workers
- summarize outcomes

The assistant is long-lived compared to workers.  It should accumulate useful
memory and context over time, but its direct execution privileges should still
be constrained by policy.

The assistant should be deployable as a persistent remote Emacs server on a
VPS, VM, or dedicated machine, reachable through =emacsclient= or messaging
gateways.  In this deployment model, Emacs remains the runtime environment for
the assistant, but the user accesses it remotely.

** Session and Memory Layer

The system should treat sessions as first-class objects rather than as merely
chat transcripts.

A session contains:

- identity and lineage
- active profile
- loaded skills
- granted capabilities
- current policies
- conversation history
- referenced artifacts
- worker lineage
- summaries and checkpoints

The memory model should distinguish between:

- short-lived conversational context
- task memory
- project memory
- user preference memory
- durable personal knowledge

The assistant should be able to reference prior tasks and outcomes without
replaying entire transcripts.

** Plugin Layer

This layer provides the composable capability surface of the system.  A plugin
is a single package that bundles executable power, behavioral guidance, and
integration metadata — following the model established by Claude Code and Codex
plugins.

A plugin provides:

- elisp functions callable via eval (the primary tool surface)
- capability declarations
- hooks and event triggers
- subagent/worker definitions and profiles
- prompt instructions, workflows, and heuristics
- schemas for invocation
- backend compatibility metadata

Because the assistant runs in Emacs, plugins are essentially Emacs packages.
The assistant can evaluate plugin-provided functions directly, and can extend
or customize them at runtime.

Examples of plugins:

- =org=: node lookup, capture, refile, agenda, state changes, planning guidance
- =magit=: diff, log, stage/unstage, commit drafting, git workflow heuristics
- =project=: project roots, file sets, symbol maps, search, coding conventions
- =diagnostics=: flymake/flycheck, compilation errors, LSP diagnostics
- =mail=: thread inspection, draft composition, triage workflows
- =browser=: site interaction, scraping, research heuristics
- =coding=: coding worker profiles, test/build loop guidance, artifact review

** Capability and Policy Layer

This layer determines what a session or worker is allowed to do.

A capability grant includes at least:

- capability identifier
- scope
- backend constraints
- duration
- escalation rules

Scope may include:

- filesystem roots
- repositories
- org files or node subsets
- mail accounts
- network domains
- process classes
- worker types

Policies can be:

- global
- per-user
- per-project
- per-session
- per-worker

The system should support session-scoped grants where the assistant identifies
likely required permissions up front and asks once, rather than repeatedly.

** Worker Subagent Layer

This layer governs the creation, lifecycle, and artifact return of worker
subagents.  Delegation is modeled as a tool call: the assistant spawns a worker
into a sandbox, the worker runs autonomously, and the results are returned as
a structured artifact envelope.

*** Spawning

The assistant spawns a worker by invoking a tool call that specifies:

- task objective
- worker class
- execution backend
- capability envelope
- resource budgets
- desired outputs

This is analogous to Claude Code's =Agent= tool or Codex's subagent spawning.

*** Worker Lifecycle

A worker has:

- a task contract
- a capability envelope
- an execution backend
- a set of active plugins
- budgets and limits
- a stable artifacts directory

Workers are disposable by default.  They should be easy to spin up, inspect,
or discard.

*** Artifact Sync and Sandbox Teardown

The tricky constraint is that sandbox environments are transient, but artifact
retrieval may be asynchronous.  The solution:

- Every worker has a stable artifacts directory (e.g. =/artifacts/worker-NNN/=)
  inside the sandbox.
- The worker writes all outputs to this directory: patches, logs, summaries,
  test results, the structured manifest.
- A *lifecycle hook on sandbox teardown* automatically syncs the artifacts
  directory back to the control plane before the sandbox is destroyed.
- This ensures artifacts are preserved even if the control plane does not
  immediately consume them, and even if the sandbox is torn down due to
  timeout, budget exhaustion, or explicit cancellation.

The sync mechanism in the initial implementation can be as simple as =rsync= or
=scp= from the VM to a local artifacts store on the Emacs host.

** Sandbox and Backend Layer

This layer provides the actual execution environments used by workers and, in
some cases, by the control plane.

Backend classes may include:

- host
- local restricted runner
- local sandbox
- VM sandbox
- remote VM sandbox
- browser sandbox

For coding workflows, VM-based sandboxes are the intended default.

** Artifact and Review Layer

This layer standardizes what workers return and how the control plane reasons
about their output.

Artifacts include:

- patches
- file trees
- command traces
- test reports
- build logs
- screenshots
- structured summaries
- proposed org updates
- drafted communications

The review layer should let the assistant and the user inspect artifacts before
they are applied to important host state.

** Emacs Environment (Native Capabilities)

Because Emacs is the runtime, the assistant has native access to the full Emacs
environment.  There is no separate "host integration layer" — the assistant is
the Emacs process.

Native capabilities exposed through plugins include:

- buffers and windows
- project state (project.el)
- org-mode (agenda, capture, refile, properties, etc.)
- mail (notmuch, mu4e, gnus, etc.)
- xref, imenu, diagnostics, syntax tree access
- documentation lookup
- UI navigation and notifications
- elisp evaluation and runtime extension

These capabilities should still be mediated through plugins and capability
grants, not as unrestricted ambient authority.  Some native actions are
low-risk (inspecting a buffer), while others are identity-bearing or
destructive (sending email, mutating org state).

** Observability and Audit Layer

The system should record:

- user-visible actions
- capability grants and denials
- worker creation and lineage
- backend selection
- artifact production
- host application of results
- escalations
- failures and policy violations

The purpose is not just debugging.  It is also trust: the user should be able
to understand what happened and why.


* Agent Hierarchy

** Primary Agent: Personal Assistant

The primary agent is a long-lived Emacs process that serves as the user's
interface to the system.

It is responsible for:

- conversation
- memory
- context management
- plugin activation
- policy interpretation
- worker subagent spawning and monitoring
- artifact review and integration

It may perform low-risk actions directly via elisp evaluation, but it should
prefer delegation for risky or execution-heavy tasks.

** Worker Subagents

Workers are task-scoped agents spawned by the assistant via tool calls.

A worker may be:

- coding-oriented (repo edits, tests, builds)
- browser-oriented (site interaction, scraping)
- shell-oriented (command execution, automation)
- drafting-oriented (prose, summaries, rewrites)
- research-oriented (web queries, note extraction)

Workers should be selected based on:

- task shape
- risk level
- required capabilities
- needed backend

** Recursive Delegation

In advanced forms, workers may themselves spawn sub-workers.  However, the
system should treat recursive delegation as a policy-governed behavior rather
than a default assumption.

The control plane should remain the primary owner of:

- top-level policy
- final integration
- irreversible actions


* Capability Model

** Capability Categories

Capabilities should be grouped into comprehensible families.

Examples:

- *Project Read*: read repo files, search project, inspect git state
- *Project Write*: modify repo files, apply patches, write generated files
- *Project Execute*: run build, test, lint, format, shell commands
- *Network Access*: outbound HTTP, package fetch, API calls
- *Host Editor Read*: inspect buffers, windows, symbols, diagnostics
- *Host Editor Write*: edit buffers, rearrange windows, update local state
- *Org Read*: lookup nodes, agenda, backlinks, metadata
- *Org Write*: capture, update nodes, refile, set state
- *Mail Draft*: search mail, open threads, draft replies
- *Mail Send*: transmit mail or messages
- *Identity-Bearing Actions*: push commits, send communications, publish changes

** Scope

Capabilities should be scoped to concrete boundaries.

Examples:

- one repository
- one subtree of the filesystem
- one org file
- a set of org ids
- one mail account
- an allowlist of network domains
- one worker session

** Duration

Capabilities should have duration semantics.

Examples:

- single action
- current conversation session
- current project session
- persistent project policy
- one worker lifetime

** Grant Sources

Capabilities may be granted by:

- default policy
- user profile
- project policy
- explicit user approval
- a prior negotiated capability bundle

** Escalation

A session or worker may request capability escalation if it determines that
additional power is likely required.

An escalation request should include:

- requested capabilities
- rationale
- expected duration
- expected backend
- expected outputs or side effects


* Plugins

A plugin is a package that bundles executable authority, behavioral guidance,
and integration metadata into a single unit.  This follows the model
established by Claude Code plugins (https://code.claude.com/docs/en/plugins)
and Codex plugins (https://developers.openai.com/codex/plugins/build).

In Benedict's Emacs-native architecture, a plugin is essentially an Emacs
package.  The assistant can evaluate plugin-provided elisp functions directly,
customize them at runtime, and extend them dynamically.

** Plugin Contents

A plugin should declare:

- plugin id
- provided capabilities
- elisp functions (callable via eval)
- hooks and event triggers
- subagent/worker definitions and profiles
- schemas for invocation
- prompt instructions, workflows, and heuristics
- backend compatibility
- side effect class
- required dependencies

** Examples

- an =org= plugin could expose org lookup, node mutation, agenda querying,
  capture helpers, and planning heuristics
- a =magit= plugin could expose diff summary, commit history, stage/unstage,
  commit-draft generation, and git workflow guidance
- a =project= plugin could expose project roots, file sets, symbol maps,
  search operations, and coding conventions
- a =coding= plugin could define coding worker profiles, test/build loop
  heuristics, and artifact review guidance

** Plugin Activation

Plugins may be activated by:

- user request
- project defaults
- assistant inference
- worker profile selection

Plugin activation should not automatically imply broad authority.  It should
influence behavior and recommended capabilities, but actual power comes from
capability grants.


* Control Plane

** Responsibilities

The control plane is the Emacs-based assistant process responsible for:

- maintaining the user relationship
- interpreting natural language requests
- activating plugins and binding capabilities
- gathering context from the Emacs environment
- evaluating elisp for direct actions
- brokering capability grants
- spawning and monitoring worker subagents
- reviewing artifacts and presenting final results

** Direct Action by the Control Plane

The control plane may act directly via elisp evaluation when the work is:

- low-risk
- tightly coupled to live Emacs state
- easy to undo
- not execution-heavy
- not well served by delegation

Examples:

- answer questions about the current buffer
- open or navigate to a file, symbol, or org node
- summarize mail or notes
- prepare a worker task from current context
- apply a reviewed patch to the local checkout
- define new elisp functions to extend capabilities

** When the Control Plane Should Delegate

The control plane should prefer delegation to a worker subagent when the work
is:

- command-heavy
- long-running
- risky
- parallelizable
- likely to benefit from isolation
- likely to produce artifacts for review

Examples:

- coding tasks
- debugging and test loops
- package manager interactions
- web automation
- scraping or research jobs
- document conversion or batch processing


* Worker Plane

** Worker Contract

Every worker subagent should have a contract describing:

- task objective
- allowed capabilities
- execution backend
- resource budgets
- desired outputs (artifact types)
- escalation rules
- completion conditions

** Worker Classes

The system may define standard worker classes as part of plugins.

Examples:

- *Coding Worker*: repo edits, shell, git, tests, optional network
- *Browser Worker*: site interaction, downloads, scraping, constrained network
- *Research Worker*: web queries, note extraction, citation gathering
- *Drafting Worker*: constrained writing and transformation
- *Local Sandbox Worker*: shell and filesystem in a local constrained runner

** Artifact Envelope

Workers return a structured artifact envelope to the control plane.  The
envelope is a manifest (JSON or S-expression) stored in the worker's stable
artifacts directory along with the referenced files.

An artifact envelope contains:

- summary (structured description of what was done)
- patches (git format-patch files for code changes)
- command trace / logs
- test results and build logs
- exceptions and errors
- open questions
- requested escalations
- suggested next steps

Example envelope for a coding worker:

#+begin_example
{
  "worker_id": "worker-001",
  "task": "Fix failing test in auth-middleware",
  "status": "completed",
  "summary": "Root cause was a missing null check in token validation...",
  "patches": ["0001-fix-auth-middleware-null-check.patch"],
  "test_log": "test-results.log",
  "commands_run": ["npm test", "npm run lint"],
  "open_questions": [],
  "escalations": []
}
#+end_example

The control plane should be able to consume worker output by reading the
envelope manifest, without replaying the worker's transcript.

** Artifact Transfer

The transfer mechanism from sandbox to control plane:

1. The worker commits changes to a local branch inside the sandbox.
2. The worker runs =git format-patch= to produce patch files.
3. The worker writes the envelope manifest and all artifact files to the
   stable artifacts directory (=/artifacts/worker-NNN/=).
4. On sandbox teardown, a lifecycle hook syncs the artifacts directory to the
   control plane via =rsync= or =scp=.
5. The control plane reads the manifest and decides whether to apply, review,
   or discard the results.
6. If applying, the control plane uses =git am= to apply patches to the local
   checkout.

This gives us git-native change transfer (handles binaries, preserves
authorship), structured metadata alongside the patches, and no shared mutable
state between the sandbox and the host.


* Sandbox and Backend Model

** Backend Types

The system should support multiple backend classes because different tasks need
different execution environments.

*** Host Backend

The host backend operates in the user's live environment.

Use cases:

- host-native editor interactions
- org and mail actions
- direct UI manipulation

Risks:

- highest blast radius
- must be tightly capability-gated

*** Local Restricted Runner

This backend is a lightweight local command environment.

Characteristics:

- filtered environment variables
- restricted command surface
- controlled working directory
- optional fake or overlay filesystem
- optional no-network mode

Use cases:

- quick shell tasks
- tests of command flows
- low-cost local delegation

*** Local Sandbox

This backend is a stronger local isolation environment, such as a temporary
workspace, copy-on-write checkout, container, or equivalent constrained runtime.

Use cases:

- local coding workflows
- build/test loops
- safe experimentation

*** VM Sandbox

This backend is a VM-based execution environment, such as a NixOS machine
running locally.

Characteristics:

- strong isolation
- reproducible image
- explicit network controls
- full shell and process execution inside the guest

Use cases:

- default autonomous coding work
- trusted test/build/package manager interactions
- local high-autonomy workers

*** Remote VM Sandbox

This backend is a VM or VM-like environment running remotely.

Characteristics:

- strong separation from host
- suitable for long-running or high-risk tasks
- supports remote worker pools

Use cases:

- autonomous coding
- externalized worker fleets
- heavy or parallel jobs

** VM-Centric Coding Model

The preferred coding workflow in this design is:

1. Assistant gathers intent and context from the Emacs environment.
2. Assistant spawns a coding worker subagent into a remote VM via tool call.
3. Worker receives a repo clone or materialized branch inside the VM.
4. Worker edits, builds, tests, and commits inside the VM.
5. Worker writes artifact envelope (patches, logs, summary) to the stable
   artifacts directory.
6. On sandbox teardown, the lifecycle hook syncs artifacts back to the control
   plane.
7. Assistant reviews the envelope and applies patches to the local checkout
   (via =git am=) or presents them for user review.

This approach shifts trust from interactive approvals to environment design.

** Network Control

Network access should be enforced at the backend layer, especially for VM-based
workers.

Policies may include:

- no network
- domain allowlist
- package registry only
- unrestricted outbound

Network policy should be attached to capability and backend configuration, not
left mainly to prompt instructions.

** Why NixOS VM Backends Fit

NixOS VMs are attractive because they provide:

- reproducible environments
- clean dependency specification
- parity between local and remote workers
- explicit image configuration
- composability with infrastructure automation

This makes them a good default for coding workers.


* Temporal Primitives and Event-Driven Behavior

A personal assistant that only responds to direct invocation is a chatbot.  To
behave as an always-on assistant, the system needs temporal primitives.

** Timers and Scheduled Actions

The assistant should be able to schedule future actions:

- *Cron-like timers*: recurring actions at specified intervals (e.g., check for
  new mail every 5 minutes, summarize today's agenda at 9am)
- *One-shot timers*: deferred actions (e.g., remind me about this in 2 hours)
- *Idle timers*: actions triggered when the user has been idle (e.g.,
  background indexing, memory compaction)

In Emacs, these map naturally to =run-at-time=, =run-with-idle-timer=, and
similar primitives.

** Event Hooks and Triggers

The assistant should be able to register interest in events:

- =after-save-hook=: react to file saves (e.g., run tests, update diagnostics)
- =org-after-todo-state-change-hook=: react to org state changes
- =file-notify=: react to filesystem changes
- Mail arrival notifications
- Git state changes (new commits, branch switches)
- Custom application events

Hooks allow the assistant to be *reactive* rather than purely *responsive*.

** Callback-Style Coordination

When the assistant delegates work to a worker subagent, the completion of that
work is itself an event.  The assistant should be able to register a callback
for worker completion, so it can automatically review artifacts, notify the
user, or chain further work.

** Relationship to Plugins

Temporal primitives should be declarable within plugins.  For example, a mail
plugin might register a timer to poll for new messages, and an org plugin might
register hooks on todo state changes.  The assistant's temporal behavior is
therefore composable through plugin activation.


* Self-Evolution and Runtime Extensibility

One of the most distinctive properties of an Emacs-based agent is the ability
to evolve its own capabilities at runtime.

** Mechanisms

Because the assistant runs in Emacs, it can:

- =defun= new functions, creating new tools on the fly
- =advice-add= to existing functions, modifying behavior
- =eval= arbitrary elisp, including package installation
- Define new interactive commands
- Register new hooks and event triggers
- Modify its own prompt instructions or plugin configuration

This means the assistant can, within a single session:

- notice a recurring pattern and define a helper function for it
- install a package to gain new capabilities
- wrap an existing function with logging or safety checks
- create a new worker profile for a novel task type

** Governance

Self-evolution is the most powerful and most dangerous capability.  It should
be governed by:

- capability grants (the ability to eval arbitrary elisp is itself a capability)
- audit logging (every eval should be recorded)
- reversibility (prefer =advice-add= over destructive redefinition, keep
  before/after state)
- user review for persistent changes (ephemeral helpers are fine; rewriting
  core functions should require confirmation)


* Approval and Permission Model

** Shift in Philosophy

The old approval model is:

- tool call requested
- user approves call
- tool runs

The new model is:

- session or worker subagent is granted a capability envelope
- most actions inside that envelope run autonomously in the sandbox
- escalations and final external effects are reviewed explicitly

** Approval Lanes

The system should support several lanes of trust.

*** Autonomous in Sandbox

Actions run without user interruption because the worker environment is already
bounded enough.

Examples:

- repo edits in a VM clone
- running tests in a VM
- package installation in a disposable worker

*** Session-Scoped Grant

The user grants a bundle of capabilities at the beginning of a session or task.

Examples:

- allow project read/write in VM sandbox
- allow git and shell commands in coding workers
- allow org read on host

*** Mid-Session Escalation

The assistant or worker requests more authority with a rationale.

Examples:

- enabling outbound network for documentation lookup
- allowing access to another repository
- allowing org write after initial read-only planning

*** Final-Effect Confirmation

The user confirms actions that cross important trust boundaries.

Examples:

- apply patch from worker artifact to local checkout
- send email
- push branch
- publish to external service
- mutate important personal data

** Up-Front Permission Planning

The assistant should be able to ask for likely-needed permissions up front.

An up-front permission request should describe:

- the task class
- the likely worker types
- the likely capabilities needed
- the intended backends
- the likely final artifacts
- the likely external effects

This reduces interruption while preserving informed consent.


* Artifact Model

** Artifact Types

Artifacts should be first-class entities.

Examples:

- patch set
- branch ref
- file bundle
- test report
- command log
- screenshot
- scraped notes
- org patch
- drafted email
- task summary

** Artifact Lifecycle

Artifacts are:

- created by workers and written to the stable artifacts directory
- synced to the control plane via lifecycle hook on sandbox teardown
- attached to sessions via the artifact envelope manifest
- reviewed by the assistant
- optionally presented to the user
- optionally applied to Emacs/host state
- optionally persisted as memory

** Artifact Application

The application of an artifact is itself a meaningful act.

Examples:

- applying a patch to the local checkout
- importing a generated org subtree
- opening a draft email in a compose buffer
- storing research notes in project memory

The assistant should usually perform or mediate artifact application rather than
asking workers to mutate host state directly.


* Memory and Continuity

** Memory Types

The system should distinguish among:

- *Conversation Memory*: recent turns and active context
- *Task Memory*: goals, decisions, artifacts, blockers
- *Project Memory*: repository notes, conventions, recurring flows
- *Personal Memory*: preferences, routines, recurring contacts, personal
  workflows

** Assistant Memory

The assistant is the main consumer and curator of durable memory.

Workers may emit memory candidates, but they should not generally write durable
memory directly without a control-plane integration step.

** Summarization and Compaction

Long-running work should be summarized into:

- task summaries
- worker summaries
- artifact summaries
- decision logs

This keeps the system tractable over time.


* Observability and Trust

The system should support user trust by making visible:

- which agent acted
- which backend it used
- which capabilities it had
- which artifacts it produced
- what was applied to host state
- what external effects occurred

This implies a lineage model:

- user request
- assistant interpretation
- worker delegation
- worker artifact output
- assistant integration
- final effect


* User Flows

** Flow: Everyday Personal Assistance

1. The user asks the assistant to summarize the day, check pending org tasks,
   and remind them what they intended to work on.
2. The assistant uses host-native plugins for org and memory.
3. No worker is required because the actions are low-risk and host-native.
4. The assistant responds directly and may update temporary task state.

** Flow: Remote Persistent Assistant via Emacsclient

1. The assistant runs inside a long-lived Emacs session on a VPS or VM.
2. The user connects through =emacsclient= from another machine.
3. The gateway layer associates the request with the user's existing assistant
   identity, session history, and active tasks.
4. The assistant handles the request normally, using its remote host-native
   capabilities and delegating risky execution to workers as needed.
5. The response is delivered back through the =emacsclient= connection.

This preserves an Emacs-native workflow while allowing the assistant itself to
live in a persistent remote environment.

** Flow: Messaging-App Invocation

1. The user sends a message to the assistant through Slack, Discord, WhatsApp,
   or another messaging gateway.
2. The gateway authenticates the user, maps the message into the assistant's
   shared session model, and records the channel as a reply route.
3. The assistant interprets the request, consults memory and active tasks, and
   may delegate work to one or more workers.
4. The assistant replies through the same messaging channel with:
   - a direct answer
   - a progress summary
   - a clarification question
   - a request for capability escalation
   - a pointer to a richer review surface when artifact inspection is needed
5. If the task eventually requires detailed review, the assistant can hand the
   user off to Emacs or another richer client while preserving the same
   underlying session.

This enables ambient access to the assistant without requiring the user to open
Emacs first.

** Flow: Coding Task Delegation

1. The user asks the assistant to fix a failing test in a project.
2. The assistant gathers context from the Emacs environment:
   - current project and active buffers
   - local org notes
   - current git state via magit
3. The assistant activates the coding plugin and spawns a coding worker
   subagent into a remote VM via tool call.
4. The worker clones the repo inside the VM.
5. The worker reads code, edits, runs tests, and commits changes.
6. The worker writes an artifact envelope to the stable artifacts directory:
   - git format-patch files
   - test logs
   - structured summary
   - open questions if any
7. On sandbox teardown, the lifecycle hook syncs artifacts back to the control
   plane.
8. The assistant reviews the envelope, presents the summary and diff to the
   user, and applies patches via =git am= if approved.
9. If the user wants, the assistant may continue with local follow-up, such as
   updating org notes or drafting a commit message.

** Flow: Up-Front Permission Negotiation

1. The user asks for a substantial coding task.
2. The assistant predicts that it will need:
   - coding worker in remote VM
   - repo read/write in worker
   - git and shell execution in worker
   - outbound network for docs and package metadata
   - final patch application to host only after review
3. The assistant presents a single permission bundle request.
4. The user grants the bundle for the duration of the task.
5. The assistant proceeds without repeated command prompts.

** Flow: Mid-Task Escalation

1. A worker discovers that it cannot complete the task without network access.
2. The worker requests escalation through the assistant.
3. The assistant summarizes why the escalation is needed and how it will change
   the execution boundary.
4. The user grants or denies the escalation.
5. The worker resumes under the updated policy or adapts accordingly.

** Flow: Org-Backed Planning and Execution

1. The user asks the assistant to shape a project effort.
2. The assistant reads relevant org nodes on host and synthesizes a plan.
3. The assistant may spawn a coding worker to perform exploratory analysis in a
   sandbox.
4. The worker returns findings and candidate patches or implementation notes.
5. The assistant updates the relevant org nodes on host, subject to org write
   capability.
6. The conversation remains centered on one personal assistant, even though both
   host and worker execution were involved.

** Flow: Risky Personal Assistant Action via Worker

1. The user asks the assistant to perform a risky shell-heavy local task.
2. Instead of acting directly, the assistant provisions a local sandbox worker.
3. The worker performs the risky execution in isolation.
4. The assistant reviews the output and applies only the desired effects.

This demonstrates that even "personal assistant work" can often be reframed as
control-plane orchestration plus worker execution.

** Flow: Drafting and Sending Email

1. The user asks the assistant to reply to an email thread.
2. The assistant uses host mail plugins to inspect the thread.
3. The assistant may optionally delegate drafting help to a drafting worker.
4. The assistant produces a draft on host.
5. Sending remains a distinct identity-bearing action requiring explicit final
   confirmation or an appropriately granted send capability.

** Flow: Parallel Coding Workers

1. The user asks for a broad refactor.
2. The assistant decomposes the task into multiple bounded worker tasks.
3. Each worker subagent operates in its own remote VM sandbox.
4. Workers return artifact envelopes (each with their own patch sets).
5. The assistant compares, merges, or sequences patches for user review.

The user still experiences one coherent assistant-driven workflow.

** Flow: Cross-Gateway Continuity

1. The user starts a conversation in Emacs.
2. Later, the user checks in from Slack or another messaging gateway.
3. The assistant continues the same underlying task, reports worker status, and
   answers questions using the same memory and artifact graph.
4. When the user returns to Emacs or =emacsclient=, they can inspect the same
   session with full history, artifacts, and review tools.

This continuity is a core property of the system: gateways are alternate
surfaces over shared assistant state, not separate silos.


* Example Worker Taxonomy

- *Coding Worker*
  Repo-focused, shell-enabled, patch-producing, remote VM-backed by default.
  Returns artifact envelope with git format-patch files, test logs, and summary.

- *Research Worker*
  Web and document oriented, network-enabled, summary-producing.

- *Browser Worker*
  Interactive browser sandbox for site operations and scraping.

- *Drafting Worker*
  Produces prose artifacts, drafts, summaries, and rewrites.

- *Local Sandbox Worker*
  Quick constrained runner for shell-oriented tasks on the local machine.


* Non-Goals

- Making every capability available directly to the personal assistant by
  default.
- Relying primarily on raw arbitrary code execution as the main extensibility
  surface.
- Treating every plugin operation as requiring immediate human confirmation.
- Using transcript replay as the only form of memory or integration.
- Assuming that all tasks should run on host or that all tasks should run
  remotely.


* Open Design Questions

- How should gateway identity, authentication, and routing be modeled so that a
  user can move fluidly among Emacs, =emacsclient=, and messaging platforms
  without fragmenting sessions?
- Which actions should be permitted from low-bandwidth gateways like chat
  platforms, and which should require handoff into a richer review surface?
- How should worker creation and lifecycle be represented in the user interface
  so that the experience stays coherent without becoming opaque?
- How aggressively should the assistant infer up-front capability bundles rather
  than asking the user for narrower grants?
- How should persistent personal memory be reviewed, corrected, or forgotten?
- How should branching, merging, and conflict resolution be surfaced when
  multiple coding workers operate in parallel?
- What is the right granularity for self-evolution governance?  When should the
  assistant be free to define new helpers vs. when should it require approval?
- How should temporal primitives (timers, hooks) interact with capability
  grants?  Should a timer-triggered action require the same approval as a
  user-triggered one?
- What is the right failure mode when artifact sync fails during sandbox
  teardown?  Retry?  Keep the sandbox alive?  Alert the user?


* First Vertical Slice

The full architecture described above is the target.  The first implementation
should validate the core architectural spine with a minimal but honest vertical
slice.

** Scope

The first slice should include:

1. *Local Emacs assistant* running as a long-lived Emacs process with basic
   plugin support (org, project, magit).
2. *Remote VM coding worker* spawned via a tool call, receiving a repo clone,
   performing edits/tests/commits, and returning an artifact envelope.
3. *Artifact envelope and transfer*: git format-patch inside a structured
   manifest, synced from the VM via lifecycle hook on teardown.
4. *Patch application*: the assistant applies patches to the local checkout
   via =git am= after review.

** Why Remote VM in the First Slice

It would be simpler to start with only local execution, but this would risk
baking in assumptions about shared filesystem access that break when sandboxing
is added later.  Including the remote VM from the start forces:

- a clean artifact transfer boundary (no shared filesystem)
- explicit serialization of worker inputs and outputs
- real sandbox lifecycle management (provision, teardown, artifact sync)
- the subagent tool call interface as the delegation primitive

These are the architectural load-bearing decisions.  Getting them right early
is more important than breadth of features.

** What the First Slice Defers

- Multiple gateways (only direct Emacs invocation)
- Messaging platform integration
- Multiple worker types (only coding workers)
- Full capability/policy engine (hardcoded capability sets)
- Temporal primitives (timers, hooks)
- Self-evolution governance
- Parallel worker coordination
- Memory beyond conversation context

** Success Criteria

The first slice is successful if a user can:

1. Ask the assistant (in Emacs) to fix a failing test.
2. The assistant gathers context and spawns a coding worker into a remote VM.
3. The worker clones the repo, makes changes, runs tests, and produces an
   artifact envelope.
4. The artifact envelope is synced back on teardown.
5. The assistant presents the summary and diff to the user.
6. The user approves and the patch is applied to the local checkout.

This validates: Emacs as runtime, subagent delegation, sandbox isolation,
artifact transfer, and patch application — the full control-plane-to-worker
round trip.


* Summary

The proposed system is centered on a long-lived personal assistant running as
an Emacs process that owns meaning, continuity, and orchestration, paired with
a worker plane of sandboxed subagents that own isolated execution.

Emacs is the runtime and operating system for the assistant, the way a shell
is Claude Code's runtime.  The assistant has native access to the full Emacs
Lisp environment and can evolve its own capabilities at runtime.

This architecture allows the system to become more autonomous without becoming
reckless:

- the assistant is an Emacs process with native access to buffers, org, mail,
  and the full elisp environment
- risky work is delegated to sandboxed worker subagents via simple tool calls
- workers return structured artifact envelopes (patches, logs, summaries)
- artifacts are automatically synced from sandboxes via lifecycle hooks on
  teardown
- capabilities are granted in scoped bundles rather than by repetitive prompts
- plugins bundle tools, hooks, subagent definitions, and behavioral guidance
- temporal primitives enable always-on assistant behavior
- the assistant can extend its own tool surface at runtime

The result is a system where autonomy is achieved primarily through isolation,
policy, and clear responsibility boundaries rather than by asking the user to
approve every step.

The assistant is not tied to a single invocation surface.  It lives in a
persistent Emacs process while being reachable through =emacsclient=, messaging
gateways, and other channels, with shared memory, shared task continuity, and
shared worker orchestration.
